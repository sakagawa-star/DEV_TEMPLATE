| ADR-3 | `CLAUDE.md` に知識の要約を残さない | **引き継ぐ**。要約を置くと二重管理になり、案件完了処理のたびに両方の同期が必要になる |
| ADR-4 | 技術スタック節はポインタ化する | **引き継ぐ**。テンプレートの `docs/TECH_STACK.md` も言語・パッケージ管理・ライブラリ一覧・実行環境を持つ。ポインタ文に「GPU 等のハードウェア制約を含む」と明記して環境依存の注意の所在を失わないようにする（honOCR は「GPU/CUDA の制約」と固有名で書いているため一般化した） |
| ADR-5 | ルート `README.md` は変更しない | **対象外**。テンプレートにルート README の雛形はない |
| ADR-6 | 無改変転記とし内容の整理は行わない | **読み替え**。テンプレートの移動対象はプレースホルダのため転記の同一性検証は不要。ただし「テストデータ」節のみ、節名を「データ」に改め記入例を拡張する（下記） |
| ADR-7 | update 案件の定義に但し書きを加える | **引き継ぐ**（R3）。但し書きがないと知見の追記が update 案件を要すると読め、feat/bug の完了処理と矛盾する |

### 本案件固有の判断1: R3 の但し書きを honOCR 版から変更する

honOCR 版の R3 は「内容の更新は各案件の完了処理で行う（update 案件の対象外）」と書いている。しかし同じ改訂の R4 は、update フロー ステップ6（完了処理）で `docs/PROJECT_KNOWLEDGE.md` のディレクトリ構成を更新することを求めており、「対象外」の断定と矛盾する（update 案件の完了処理で必要な作業が禁止と読める。codex-01 の指摘・中）。

本案件では次のように書き分ける。

- 禁止するのは「`docs/PROJECT_KNOWLEDGE.md` の内容の改訂を**目的とする** update 案件の起票」である
- update 案件の完了処理でファイルの追加・削除をディレクトリ構成へ反映することは、ステップ6 のとおり**行う**
- 構成変更（分割・セクション再編）は update 案件で扱う（honOCR と同じ）

honOCR にも同じ矛盾があるが、honOCR 側への逆還元は本案件のスコープ外（README「スコープ外」）。

### 本案件固有の判断2: 「テストデータ」節を「データ」に改める

テンプレートの現行節名は「テストデータ」で、記入例も「テストデータの配置場所と各ファイルの用途」に限定されている。しかし `docs/PROJECT_KNOWLEDGE.md` は honOCR のように**実データの所在と仕様**を書く場所でもあり、テストデータに限定すると実データの置き場所がなくなる。honOCR の節名「データ」に統一し、記入例を「実データ・テストデータの双方を対象とする」に拡張する。テンプレートの「テスト」節（`tests/` の規約）は `template/CLAUDE.md` 側に残るため、テストデータの記述場所が失われることはない。
