## 1. 経緯

DEV_TEMPLATE は honOCR の update-002（レビュー収束条件の明文化）と update-003（プロジェクト知識の外出し）を、それぞれ update-008・update-009 としてテンプレートへ取り込んだ。その過程の Codex レビューで、**honOCR 版の記述に2件の矛盾**が見つかった。テンプレート側では修正して取り込んだが、**honOCR 本体には矛盾が残っている**。

## 2. 修正1: 全文ゲート（C）の上限単位と criteria lock の衝突

### 2.1 問題

`CLAUDE.md` の「レビューの進め方」（update-002 で導入）は、全文ゲート C を **「案件（細分化して並列に進める場合は細分化単位）につき1回だけ」** と定めている（194行目・203行目）。

一方、同じ `CLAUDE.md` の「実験・検証の進め方」（106行目、criteria lock）は、**同一案件内で criteria 文書に対しても別途 Codex レビューと高・中ゼロへの収束を要求**し、結果を案件の `reviews/` に連番を進めて保存すると定めている。

このため、機能追加案件のステップ4 のレビューで C を使った後に criteria 文書のレビューを行うと、次のいずれかになる。

- C を実施できない（「案件につき1回」に抵触）→ 収束の定義（ゲートの会話で高・中ゼロ）を満たせず、人レビューの前提2条件も満たせない
- 「逸脱の禁止」（遷移表にない動きをしない）により、別サイクルを始めることもできない

結果として、**criteria lock を伴う実験案件が運用不能になる**。

### 2.2 発見の経緯

DEV_TEMPLATE update-008 の Codex レビュー codex-01（2026-09-04、gpt-5.6-terra medium）が重要度「高」として指摘した。指摘の全文は `docs/issues/update-008-from-honocr-review-convergence/reviews/codex-01.result.md` にある。

### 2.3 テンプレート側で採った解決

C の上限単位を「案件」から **「レビュー単位」** に変更した。レビュー単位とは、初回レビュー（A）で対象ファイルとして指定した文書一式である。

- 案件のフローのステップ4 のレビュー対象（requirements.md / design.md 等）は案件につき1単位
- 案件を細分化して並列に進める場合は細分化単位ごとに1単位
- 実験・検証の criteria 文書のレビュー（criteria lock）は criteria 文書ごとに1単位

新しいレビュー単位のレビューは遷移表の「（開始時）」の行から始める（同一案件のストリームで続けてよい。結果の保存は案件の連番を進める）。

「1回ゲート型」の趣旨（同じ文書一式に「新しい目」を2回使わない）は変わらない。

## 3. 修正2: update 案件の定義と完了処理の矛盾

### 3.1 問題

`CLAUDE.md` 77行目（update-003 で導入した但し書き）は、`docs/PROJECT_KNOWLEDGE.md` について **「内容の更新は各案件の完了処理で行う（update 案件の対象外）」** と断定している。

一方、同じ `CLAUDE.md` 94行目（ドキュメント更新フロー ステップ6・完了処理）は、**update 案件の完了処理で `docs/PROJECT_KNOWLEDGE.md` のディレクトリ構成を最新に更新する**ことを求めている。

「update 案件の対象外」を字義どおり読むと、94行目が求める作業が禁止と読める。update 案件の完了処理で必要な作業とフローの定義が矛盾する。

### 3.2 発見の経緯

DEV_TEMPLATE update-009 の Codex レビュー codex-01（2026-09-04、gpt-5.6-terra medium）が重要度「中」として指摘した。指摘の全文は `docs/issues/update-009-from-honocr-project-knowledge/reviews/codex-01.result.md` にある。

### 3.3 テンプレート側で採った解決

禁止対象を限定して書き分けた。

- 禁止するのは「`docs/PROJECT_KNOWLEDGE.md` の内容の改訂を**目的とする** update 案件の起票」である
- update 案件の完了処理でファイルの追加・削除をディレクトリ構成へ反映することは、ステップ6 のとおり**行う**
- 構成変更（分割・セクション再編）は update 案件で扱う（変更なし）

### 3.4 honOCR で行う変更（1箇所）

#### 変更 2-A: `CLAUDE.md` 77行目

**置換前**（次の太字部分が1回だけ存在することを確認済み。行全体ではなくこの部分文字列を置換する）:

```
**`docs/PROJECT_KNOWLEDGE.md` は運用ドキュメントではなく、内容の更新は各案件の完了処理で行う（update 案件の対象外）。ただし同ファイルの構成変更（分割・セクション再編）は update 案件とする。**
```

**置換後**:

```
**`docs/PROJECT_KNOWLEDGE.md` は運用ドキュメントではないため、その内容の改訂を目的とする update 案件は起票しない（知見・データ状態の追記は各案件の完了処理で行う）。update 案件の完了処理でファイルの追加・削除をディレクトリ構成へ反映することは、本フローのステップ6 のとおり行う。同ファイルの構成変更（分割・セクション再編）は update 案件とする。**
```
