**内容**: feat 案件を「ロードマップ（`roadmap.md`）＋ 1個以上のマイルストーン（`m{番号}-{slug}/` 配下の `requirements.md` / `design.md`）」で構成する。
マイルストーンが1個の案件も同じ手順を踏む（手順を案件規模で変えない）。開発方針「小さく作って動作確認し、次へ進む」を機械的に守るための規定で、
lift2d の人レビューで3回差し戻された末に確定した形（任意の別方式 → 1個の場合が従来手順になる統一手順、行数基準 → 機能構成の4境界、

## 留意事項（design.md 作成時に決めること）

### A. ルート `AGENTS.md`（本リポジトリ自身）の扱い

**lift2d の `AGENTS.md` の設計思想**（lift2d update-006 README 調査3・design.md 改訂履歴・codex-03〜06 より）:
`AGENTS.md` は規定そのものを持たず、**規定の所在**（案件種別に対応する CLAUDE.md のフロー節と、そこから参照される節・基準書）と
**判定手順**（案件フォルダ単位と対象文書単位の2段階）だけを指定し、情報源から一意に決まらない場合は「判定不能」を**高**で報告させる。
Codex が提案した「`AGENTS.md` に文書ごとの工程と規定の対応表を置く」案は CLAUDE.md の規定の再掲（二重管理）になるため不採用とし、
行き詰まり検出を発動して上記の形に切り替えた経緯がある。「判定不能・高」は不具合ではなく、**規定の穴を裁量で埋めさせず CLAUDE.md 側の欠陥として表面化させる信号**である。

**本リポジトリでの帰結**: ルート `CLAUDE.md` は「開発方針」節を持たず、update 案件の手順は「テンプレート改訂フロー（update-XXX 案件）」に書かれている。
候補2 の文面をそのままルート `AGENTS.md` に置くと、Codex は参照先（「開発方針」配下のドキュメント更新フロー）を見つけられず「判定不能・高」を報告する。
これは設計どおりの信号であり、対処は**検査を外すことではなく、参照先を本リポジトリの規定に合わせること**である。

**方針（design.md で具体化）**: ルート `AGENTS.md` には、候補2 の項目を本リポジトリ向けに参照先だけ読み替えた版を置く。

- 案件種別: 本リポジトリの案件は update のみ（`docs/issues/update-{number}-{slug}/`）
- 読む規定: ルート `CLAUDE.md`「テンプレート改訂フロー（update-XXX 案件）」と、そこから参照される節（ステップ4 の読み替えを介した `template/CLAUDE.md`「Codexによるレビューの実行方法（Herdr 対話方式）」の該当小節）
- 案件フォルダ単位: ステップ4（レビュー）の時点で `README.md`・`design.md`・`reviews/` が揃い、規定の場所にあるか
- 対象文書単位: `README.md` にステップ2 が定める内容（反映元パス・調査結果・反映対象の選別と理由）、`design.md` にステップ3 が定める内容（どのテンプレートファイルに・どのように反映するか。自己完結・曖昧表現禁止）があるか
- 判定手順の2段階・「判定不能は高で報告し、残る間は収束扱いにしない」・`reviews/` 配下と未指定文書の除外は雛形と同じ

あわせてルート `CLAUDE.md` のディレクトリ構成の `AGENTS.md` 行（「`template/AGENTS.md` と同一内容」）を、「規定適合確認の参照先を本リポジトリ向けに読み替えた版」に改める。
ルート `CLAUDE.md` は本来「本リポジトリ向けの読み替えだけを書く」層なので、ルート `AGENTS.md` の参照先が雛形と異なることは二重管理には当たらない。

**反映時の注意**: `AGENTS.md` は codex 起動時にのみ読まれる。本案件のレビューストリーム（`rev-devtmpl-update-011`）は反映前のルート `AGENTS.md` で回り、完了処理で `/quit` する。
反映後の最初の update 案件のレビューで、「[AGENTS.md適用]」マーカーと規定適合の判定が回答に含まれることを確認する（lift2d update-006 の動作確認と同じ方式）。
